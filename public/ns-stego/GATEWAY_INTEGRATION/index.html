Gateway Integration (Exchange + Postfix)¶

Overview This guide describes how to integrate Nicrypt‑Stego header verification into enterprise mail gateways. The target outcome is automatic verification and stamping of inbound messages using X‑Provenance headers.

Common Header Set - X-Provenance-Ciphertext - X-Provenance-Model - X-Provenance-BPT - X-Provenance-Timestamp - X-Provenance-KeyId

Verification Endpoint Use the API endpoint: POST /v1/provenance/verify_headers Body: { "headers": { "From": "Acme Bank alerts@yourbank.com", "X-Provenance-Ciphertext": "gAAAAA...", "X-Provenance-Model": "sshleifer/tiny-gpt2", "X-Provenance-BPT": "4", "X-Provenance-Timestamp": "2026-02-15T12:00:00Z" } }

The response includes: - verified: true|false - secret: extracted provenance - model_hash - policy: enforcement result

Exchange (Microsoft 365 / On‑Prem)

Option A: Transport Rule + Connector (Recommended) 1) Create a transport rule to detect messages with X‑Provenance‑Ciphertext. 2) Route those messages to a verification service (HTTP). 3) The service returns a stamp header: - X-Provenance-Verified: true|false - X-Provenance-Reason: ok|missing_provenance|not_detected 4) Exchange applies the stamp headers to the message and delivers it.

Option B: Transport Agent (On‑Prem) 1) Install a custom transport agent that: - extracts the headers - calls /v1/provenance/verify_headers - stamps X‑Provenance‑Verified headers 2) Enforce policy based on apps/api/server/config/policy.yaml.

Exchange Transport Rule Example (PowerShell)

New-TransportRule -Name "Provenance Verify" `
  -HeaderContainsMessageHeader "X-Provenance-Ciphertext" `
  -HeaderContainsWords "gAAAAA" `
  -SetHeaderName "X-Provenance-Verify" `
  -SetHeaderValue "true"

Exchange Connector + Verification Service Create a connector or transport rule to route messages to your verification service, then add headers based on the response:

X-Provenance-Verified: true|false
X-Provenance-Reason: ok|missing_provenance|not_detected

Exchange Transport Agent Skeleton See poc/exchange_transport_agent.cs for a minimal conceptual skeleton.

Exchange Agent Runbook See docs/EXCHANGE_AGENT_RUNBOOK.md for install and rollback steps.

Postfix

Option A: Before‑Queue Content Filter 1) Configure a content filter that reads inbound headers. 2) Call /v1/provenance/verify_headers. 3) Stamp headers and re‑inject the message.

Option B: Milter 1) Create a milter that: - inspects headers - calls /v1/provenance/verify_headers - adds X‑Provenance‑Verified headers

Postfix Config Example (content filter)

main.cf

content_filter = provfilter:127.0.0.1:2526

master.cf

provfilter unix  -       -       n       -       10      smtp
  -o smtp_destination_concurrency_limit=10
  -o smtp_send_xforward_command=yes
  -o disable_dns_lookups=yes
  -o receive_override_options=no_header_body_checks
  -o smtp_generic_maps=

Milter Stub (header stamping) Use a milter to call /v1/provenance/verify_headers and add:

X-Provenance-Verified: true|false
X-Provenance-Reason: ok|missing_provenance|not_detected

See poc/milter_stub.py for a minimal header stamping example.

Working Milter (Postfix) See poc/postfix_milter.py (requires pymilter).

Postfix Milter Config Example main.cf

smtpd_milters = unix:/var/run/provenance_milter.sock
non_smtpd_milters = $smtpd_milters
milter_default_action = accept
milter_protocol = 6

Reference PoC Tools - poc/gateway_stamp.py reads headers from .eml and prints stamp headers. - poc/verify_headers.py reads headers and prints verification output.

Operator Runbook 1) Start API and ensure JWT secrets are set. 2) Validate with a known good email (.eml). 3) Enable stamping on a pilot sender domain. 4) Monitor audit logs for verification rates and failures. 5) Roll out to additional domains.

Rollback - Disable the transport rule or content filter. - Remove X‑Provenance‑Verified headers from downstream clients if needed.
