Email & Social Media Deployment Guide¶

Overview This guide explains how to use Nicrypt-Stego for email and social media content. These channels are viable, but they apply transformations (formatting, truncation, normalization) that can reduce extraction reliability. The goal is to keep payloads small, use conservative settings, and validate retrieval in the same channel you publish to.

Email (Gmail and other providers) Recommended approach - Use plaintext or minimally formatted HTML. - Keep payloads short (e.g., owner + date + license). - Prefer bits_per_token=3 or 4 for short emails to reduce token count. - Use max_new_tokens with a safe margin (e.g., 400+ for MVP, 400+ for LLM tiny tests).

Common transformations to watch - Line wrapping and whitespace normalization. - Signature insertion or footers. - Auto-linking (URLs, emails). - Mobile clients that reflow text.

Gmail test case (end-to-end) 1) Create a stego email body Use the API to embed a short secret into a short email body:

curl -s -X POST http://localhost:8000/v1/provenance/embed \
  -H "Authorization: Bearer test-token" \
  -H "X-Scopes: provenance:embed" \
  -H "Content-Type: application/json" \
  -d '{"secret":"alice@example.com|2026-02-15|CC-BY-NC","cover_prompt":"Subject: Policy Update\n\nHello team,\nHere is the updated retention policy memo for review.\n\nThanks,\nLegal Ops","backend":"mvp","bits_per_token":3,"max_new_tokens":600}'

2) Paste the stego_text into Gmail - Compose a new email in Gmail. - Paste the returned stego_text as the email body. - Send to a test address you control.

3) Verify extraction from the received email - Copy the received email body text (avoid quoted history). - Use the verify endpoint:

curl -s -X POST http://localhost:8000/v1/provenance/verify \
  -H "Authorization: Bearer test-token" \
  -H "X-Scopes: provenance:verify" \
  -H "Content-Type: application/json" \
  -d '{"stego_text":"<PASTE_EMAIL_BODY>","backend":"mvp","bits_per_token":3,"max_new_tokens":600}'

If verified, the response will include the secret. If it fails, reduce formatting, shorten the secret, or increase bits_per_token.

Scripted demo (recommended)

TOKEN="<JWT_BEARER>" BASE_URL="http://127.0.0.1:8000/v1" scripts/gmail_demo.sh

Verify from clipboard

MODE=verify TOKEN="<JWT_BEARER>" BASE_URL="http://127.0.0.1:8000/v1" scripts/gmail_demo.sh

Verify from clipboard to file

MODE=verify-clipboard TOKEN="<JWT_BEARER>" BASE_URL="http://127.0.0.1:8000/v1" scripts/gmail_demo.sh

Verify from file

MODE=verify-file VERIFY_FILE="/tmp/gmail_body.txt" TOKEN="<JWT_BEARER>" BASE_URL="http://127.0.0.1:8000/v1" scripts/gmail_demo.sh

Social media Recommended approach - Keep secrets very short (e.g., owner|date|license). - Increase bits_per_token to reduce output length. - Use the MVP backend for deterministic behavior in tests. - Expect lower reliability due to platform normalization or truncation.

Platform-specific notes - X/Twitter: strict length limits; use only tiny payloads. Verification is brittle. - LinkedIn/Facebook: better for longer posts; still may normalize whitespace. - Medium/Substack: long-form posts work best for provenance embedding.

Operational tips - Keep a baseline “clean” stego text in logs for comparison. - Store the original secret and model settings used. - Add a fallback verification route that allows minor edits (future robustness work).
