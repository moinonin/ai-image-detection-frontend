Nicrypt-Stego: Cryptographic Provenance via LLM Steganography¶

Software Specification Document Version: 0.1.0 (Draft) Date: 2026-02-12 Authors: Derived from research insights and the Nicrypt encryption package.

  1. Introduction In the current era, every piece of text published online is liable to be scraped, ingested, and memorized by large language models (LLMs). Once data enters a model’s weights, it cannot be reliably removed, and the original author loses all control and attribution. Traditional digital signatures or watermarks are easily stripped during scraping, and post-hoc authorship claims rely on non‑cryptographic stylometry.

Nicrypt-Stego solves this problem by combining symmetric encryption with LLM‑based steganography. It allows an author to:

Encrypt a secret provenance message (e.g., author identity, timestamp, copyright notice) using the existing Nicrypt library.

Embed the resulting ciphertext into an innocuous, human‑readable cover text using token‑level steganography performed by a local LLM.

Publish the steganographic text anywhere (web, social media, PDFs).

Later recover the ciphertext from the published text and decrypt it, providing cryptographic proof of authorship.

This specification describes the architecture, components, and API for the nicrypt-stego Python package, which extends Nicrypt with state‑of‑the‑art steganographic embedding and extraction routines.

  1. Background & Related Work Research Contribution ExpShield (NDSS 2026) Proactive defense via invisible perturbations; demonstrates that data owners can prevent memorization. LLMs‑can‑hide‑text (ACL 2025) First practical method to embed secret bits into LLM‑generated text while preserving fluency and length. Infusion (ICLR 2026) Poisoning via influence‑function guided edits; shows that very few modified samples can control model behaviour. TrajPrint (S&P 2026) Lossless model fingerprinting using decodable watermarks. Nicrypt‑Stego draws directly from LLMs‑can‑hide‑text: we use its token‑selection algorithm to encode arbitrary binary data (ciphertext) into natural language. Unlike prior work that focuses on hiding plaintext secrets, we hide encrypted payloads, enabling asymmetric verification – only the key holder can prove origin.

  2. Objectives Provide a simple, pip‑installable Python library that integrates Nicrypt encryption with LLM‑based steganography.

Achieve cryptographic authorship verification: the ability to prove, beyond reasonable doubt, that a given text was authored by the holder of a secret key.

Maintain output text quality: steganographic cover texts must be grammatically correct, topically relevant, and indistinguishable from normal human‑written text.

Minimize computational overhead: use small, locally runnable open‑source LLMs (e.g., Llama‑3‑8B, Mistral‑7B) so that no API calls are required.

Support arbitrary binary ciphertext produced by Nicrypt (Fernet tokens, base64‑encoded).

  1. System Architecture The system consists of four logical layers:

text ┌─────────────────┐ │ Application │ (User code) └────────┬────────┘ │ ┌────────▼────────┐ │ nicrypt-stego │ (ProvenanceWriter / ProvenanceReader) ├─────────────────┤ │ Steganographic Engine │ (token‑level encoder/decoder) ├─────────────────┤ │ LLM Backend │ (Hugging Face transformers) └────────┬────────┘ │ ┌────────▼────────┐ │ nicrypt │ (encryption/decryption) └─────────────────┘ 4.1 Component Responsibilities Nicrypt – provides ficha(text, 'enc') and ficha(ciphertext, 'dec') using a symmetric key and salt stored in environment variables.

Steganographic Engine – converts ciphertext bits into token selections and back. Implements the algorithm described in [Shen et al. 2025].

LLM Backend – loads a pretrained causal language model and tokenizer. Used to compute next‑token probabilities.

ProvenanceWriter/Reader – high‑level facades that orchestrate encryption+embedding and extraction+decryption.

  1. Detailed Component Design 5.1 Nicrypt Integration Nicrypt is already published on PyPI. nicrypt-stego will declare it as a dependency. The encryption/decryption functions are re‑exported for convenience:

python from nicrypt.encrypt import ficha Assumption: The user has set the environment variables ENC_KEY and ENC_SALT. This is documented in Nicrypt’s own README.

5.2 Steganographic Embedder Inputs ciphertext: a base64‑encoded string (output of ficha(..., 'enc')).

cover_prompt (optional): a short phrase describing the desired topic (e.g., "a sentence about climate change").

model: a Hugging Face causal LM (default: "meta-llama/Llama-3-8B").

Algorithm (simplified) Convert the ciphertext into a bitstring (e.g., '11001010...').

For each token generation step i:

Obtain logits from the LLM given the current prefix.

Compute softmax to get probabilities over the vocabulary.

Restrict the vocabulary to the top‑k most probable tokens (k ≥ 2^b, where b is the number of bits to embed per token).

Partition the top‑k tokens into 2^b bins.

Read the next b bits from the bitstring; select the token from the corresponding bin.

Append the token and continue.

Stop when all bits are embedded (or a maximum length is reached).

Return the generated text.

Implementation notes:

Bits per token (b) is configurable (typically 1–3). Higher b increases capacity but may degrade fluency.

The algorithm must handle the final partial bits with padding.

The same random seed is used for both embedding and extraction to ensure deterministic bin assignment.

Output A string of natural language text that embeds the ciphertext.

5.3 Steganographic Extractor Inputs stego_text: the published text that contains the hidden ciphertext.

model: same model used for embedding.

Algorithm Run the LLM autoregressively on the stego text.

At each step, recompute the top‑k token bins using the same procedure as the embedder.

Observe the actual token that was used in the stego text; determine which bin it falls into.

Convert the bin index to bits and append to the reconstructed bitstring.

Continue until the end of the text (or until a stop token).

Convert the bitstring back to base64‑encoded ciphertext.

Output The original ciphertext string (or None if no valid ciphertext is found).

5.4 High‑Level API nicrypt_stego.ProvenanceWriter python class ProvenanceWriter: def init(self, model_name: str = "meta-llama/Llama-3-8B", device: str = "cpu", bits_per_token: int = 2): self.model = load_model(model_name, device) self.bpt = bits_per_token

def embed_secret(self, secret: str, cover_prompt: str, max_new_tokens: int = 100) -> str:
    """Encrypt secret, embed into generated text."""
    cipher = ficha(secret, 'enc')
    stego_text = self._embed_cipher(cipher, cover_prompt, max_new_tokens)
    return stego_text

def embed_cipher(self, cipher: str, cover_prompt: str, max_new_tokens: int = 100) -> str:
    """Embed already-encrypted ciphertext."""
    return self._embed_cipher(cipher, cover_prompt, max_new_tokens)

nicrypt_stego.ProvenanceReader python class ProvenanceReader: def init(self, model_name: str = "meta-llama/Llama-3-8B", device: str = "cpu", bits_per_token: int = 2): self.model = load_model(model_name, device) self.bpt = bits_per_token

def extract_cipher(self, stego_text: str) -> Optional[str]:
    """Extract ciphertext from stego text."""
    return self._extract_cipher(stego_text)

def extract_secret(self, stego_text: str) -> Optional[str]:
    """Extract and decrypt the secret."""
    cipher = self._extract_cipher(stego_text)
    if cipher:
        return ficha(cipher, 'dec')
    return None

Functional shortcuts python def protect(secret: str, topic: str, kwargs) -> str: """One‑shot: encrypt + embed.""" writer = ProvenanceWriter(kwargs) return writer.embed_secret(secret, topic)

def verify(stego_text: str, kwargs) -> Optional[str]: """One‑shot: extract + decrypt.""" reader = ProvenanceReader(kwargs) return reader.extract_secret(stego_text) 6. Data Flow Example python from nicrypt_stego import protect, verify

Capacity and Performance Bits/token Capacity (bytes per 100 tokens) Typical Quality 1 ~12.5 Excellent 2 25 Good 3 37.5 Acceptable 4 50 Degraded Nicrypt‑produced ciphertexts are base64‑encoded. A typical Fernet token for a short secret is ~100–200 characters. With 2 bits/token, a 200‑character (≈133‑byte) ciphertext requires ~530 tokens, which is acceptable for many use cases (short paragraphs).

  1. Security & Robustness Considerations 8.1 Key Management The same symmetric key (ENC_KEY, ENC_SALT) used for encryption is required for decryption.

Recommendation: authors should store keys in environment variables or secret managers, never hard‑coded.

Loss of key makes provenance unrecoverable.

8.2 Robustness to Text Modification The current scheme is fragile: any alteration to the stego text (paraphrasing, translation, deletion) will destroy the embedded ciphertext. This is a known limitation of token‑level steganography. Future versions may incorporate error‑correcting codes or more robust watermarking techniques (e.g., TrajPrint).

8.3 Adversarial Scenarios Stripping attack: an adversary who suspects steganography could paraphrase the text. This will break extraction. However, the adversary must do this to all text, which is costly.

Key compromise: if the symmetric key is leaked, anyone can decrypt recovered ciphertexts. This is identical to any symmetric encryption system.

8.4 Model Dependency Extraction requires the exact same LLM (and same version, device, sampling settings) used during embedding. Small variations in logits can cause bin misassignment. Solution: we store a hash of the model configuration in the embedding metadata (e.g., in the final token). The reader verifies compatibility.

  2. Integration With Veriforensic (SaaS)

This section describes how to integrate Nicrypt-Stego (ns-stego) into an existing Veriforensic-style SaaS that already has authentication (/api/v1/auth/*), subscription gating, and “resources” endpoints (e.g., classify single/batch/video).

Goal: - Make verification free (public endpoints, rate-limited). - Charge for issuance and governance (embed/issue/sign/keys/licenses) by requiring auth + subscription. - Keep source clean: ns-stego endpoints live in their own modules, while app/api.py remains the composition root.

11.1 Recommended Service Split

A) Public verify (free) - Verify sender signature tokens used by webmail verifiers. - Verify provenance markers for messages and attachments/certificates.

B) Paid issuer/admin operations - Embed provenance (stego) / encrypt. - Issue (stamp) certificates/PDFs. - Issue signature tokens (for gateway stamping). - Keys management (create/rotate/list). - License issuance and revocation (offline SDK control).

11.2 Code Organization (Avoid a 3700-Line api.py)

If all endpoints currently live in ./app/api.py, add two FastAPI routers:

  • app/routers/ns_stego_public.py
  • app/routers/ns_stego_paid.py

and (recommended) a shared proxy helper:

  • app/services/ns_stego_proxy.py

In app/api.py, only add:

from app.routers.ns_stego_public import router as ns_stego_public_router
from app.routers.ns_stego_paid import router as ns_stego_paid_router

app.include_router(ns_stego_public_router)
app.include_router(ns_stego_paid_router)

11.3 Prevent Circular Imports (Dependencies in api.py)

If get_current_active_user and get_subscription_service_dep are currently defined inside app/api.py, move them into a small dependency module:

  • app/deps.py

Then import them from both app/api.py and the routers. This avoids router ↔ api circular imports.

11.4 Configuration (Environment Variables)

SaaS -> ns-stego API configuration: - NS_STEGO_API_BASE (required): e.g. https://ns-stego.veriforensic.com/v1 - NS_STEGO_API_TOKEN (optional but typical for paid routes): service token with least privileges

Public verify strategy: - Prefer ns-stego public verify (no token required) for recipient-facing use cases. - If ns-stego verify still requires a token, store a low-privilege token server-side and enforce strict rate limits.

11.5 Endpoint Playbook (SaaS-Facing)

All routes below are SaaS routes that proxy to the ns-stego API.

11.5.1 Public Verify (No Auth)

These endpoints should NOT require Depends(get_current_active_user), but MUST be rate-limited.

1) Verify signature token - SaaS: POST /api/v1/ns-stego/verify/signature - Upstream: POST {NS_STEGO_API_BASE}/signature/verify - Request:

{ "token": "v1c...." }
  • Response (example):
{ "verified": true, "payload": { "sender": "admin@bank.com", "timestamp": "2026-02-22", "org_id": "bank" } }

2) Verify email/body markers (verdict) - SaaS: POST /api/v1/ns-stego/verify/verdict - Upstream: POST {NS_STEGO_API_BASE}/provenance/verdict - Request:

{ "headers": { "From": "admin@bank.com", "X-Provenance-Attachment": "..." }, "body_text": "...", "body_html": "..." }

3) Verify attachment markers - SaaS: POST /api/v1/ns-stego/verify/attachments - Upstream: POST {NS_STEGO_API_BASE}/provenance/verify_attachment_headers - Request:

{ "headers": { "X-Provenance-Attachment-B64": "..." } }

Abuse controls (minimum): - Payload size limits (hard cap marker size). - Per-IP and per-account (if available) rate limits. - Timeouts and circuit breakers when calling upstream.

11.5.2 Paid Issuer/Admin (Auth + Subscription)

These endpoints MUST require: - current_user: UserInDB = Depends(get_current_active_user) - subscription_service: SubscriptionService = Depends(get_subscription_service_dep)

and must enforce plan entitlements/credits before calling upstream.

Recommended paid routes:

1) Embed provenance (paid) - SaaS: POST /api/v1/ns-stego/embed - Upstream: POST {NS_STEGO_API_BASE}/provenance/embed_cipher

2) Issue certificate/PDF (paid) - SaaS: POST /api/v1/ns-stego/certificates/issue - Upstream: POST {NS_STEGO_API_BASE}/certificates/issue

3) Issue signature token (paid) - SaaS: POST /api/v1/ns-stego/signature/issue - Upstream: POST {NS_STEGO_API_BASE}/signature/issue (or /signature/token)

4) Keys management (paid/admin) - SaaS: POST /api/v1/ns-stego/keys/create -> {NS_STEGO_API_BASE}/keys - SaaS: POST /api/v1/ns-stego/keys/rotate -> {NS_STEGO_API_BASE}/keys/{key_id}/rotate - SaaS: GET /api/v1/ns-stego/keys/list -> {NS_STEGO_API_BASE}/keys

5) Licensing (paid/admin) - SaaS: POST /api/v1/ns-stego/licenses/issue -> {NS_STEGO_API_BASE}/licenses/issue - SaaS: POST /api/v1/ns-stego/licenses/revoke -> {NS_STEGO_API_BASE}/licenses/revoke

11.6 Subscription and Billing Strategy (Verify Free)

Recommended enforcement: - Public verify endpoints: free, rate-limited. - Issuance/admin endpoints: require subscription plan + enforce per-feature entitlements.

Typical metering units: - per embed call - per certificate issued - per signature issued - per key rotation / key creation - per license issued/revoked

11.7 Security Hygiene

Secrets: - Never accept ns-stego service tokens from browsers; keep them server-side. - Prefer file-based secrets in deployments where possible. - Ensure logs never include API tokens or license tokens.

TLS: - Only allow NS_STEGO_API_BASE over HTTPS in production environments.

Auditing: - Store request_id returned by ns-stego for traceability across services.

Integration tests: use small local models (e.g., "gpt2") to test full protect/verify cycles.

Fluency evaluation: compute perplexity of stego texts vs. unconstrained generation; aim for <10% degradation.

Capacity benchmarks: measure maximum embeddable bytes for different bit‑per‑token settings.

Model‑dependent Develop a calibration technique to make bin assignments model‑agnostic. Only text output Extend to other modalities (code, structured data). Manual key management Integrate with hardware security modules or cloud KMS.
  2. Conclusion Nicrypt‑Stego transforms a simple symmetric encryption utility into a complete cryptographic provenance system. By leveraging recent advances in LLM steganography, it offers the first practical, developer‑friendly tool for proving authorship in the age of ubiquitous AI training. The specification above is immediately actionable; all components are either already implemented (Nicrypt) or have public research implementations (token‑level steganography). The remaining work is integration, packaging, and user‑experience refinement.
