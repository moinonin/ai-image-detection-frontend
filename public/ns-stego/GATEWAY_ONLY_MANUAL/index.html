Gateway-Only Deployment Manual¶

Purpose Run Nicrypt-Stego entirely at mail gateways (no endpoint agents). This is the recommended production architecture for institutions with 1000+ users.

Audience - Email admins (Exchange/Postfix/SES/Brevo) - Security/IT ops - Compliance and audit teams

Design Goals - Centralized control and auditability - No endpoint installs - Consistent policy enforcement - Easy rollback and monitoring

System Components 1) Outbound Gateway (SMTP relay) - Stamps provenance headers and optional visible NS-SIGNATURE tokens. - Component: poc/smtp_relay.py

2) Inbound Gateway (SMTP verifier) - Verifies inbound headers and stamps verdict headers. - Component: poc/smtp_inbound_daemon.py

3) Verification API - REST API used by both gateways - Endpoint: /v1/provenance/verify_headers

4) Client UX (optional but recommended) - Gmail extension / Outlook add-in - Reads stamped headers and displays badges

High-Level Flow Outbound (sign + attachments): Sender -> Gateway Relay (stamp headers) -> Inbound Verifier (stamp HTML) -> SMTP Provider -> Recipient

ASCII Diagram

[Sender] -> [smtp_relay.py:2525] -> [smtp_inbound_daemon.py:2527] -> [SMTP Provider] -> [Mailbox]

Headers Used Outbound (added): - X-Provenance-Ciphertext - X-Provenance-Model - X-Provenance-BPT - X-Provenance-Timestamp - X-Provenance-KeyId

Inbound (added): - X-Provenance-Verified - X-Provenance-Reason - X-Provenance-Model-Hash - X-Provenance-Timestamp - X-Provenance-Sender-Domain

Modes 1) Header-only (recommended default) - Uses X-Provenance-* headers only. - Cleanest for deliverability and lowest risk.

2) Header + Visible Signature - Adds NS-SIGNATURE: v1c... into the email body. - Helpful for clients without header support. - Controlled by SIGNATURE_MODE=visible.

Security Model - Provenance ciphertext is encrypted using Nicrypt keys. - Verification checks decryptability + org policy (sender domain). - Tokens (NS-SIGNATURE) are HMAC signed with SIGNATURE_SECRET.

Operational Options (Exhaustive)

A) SMTP Provider Gateway (Brevo/SES/Sendgrid) Use SMTP credentials from the provider and point all outbound traffic to the relay. - Outbound relay: poc/smtp_relay.py - Inbound verifier: poc/smtp_inbound_daemon.py

B) Microsoft 365 (Exchange Online) - Recommended Outbound (via M365 Connector) 1) Create an Exchange Online outbound connector to your gateway relay host:2525. 2) Route all mail (or pilot domain) through the connector. 3) Ensure the relay forwards to your SMTP provider (or directly to MX).

Inbound (via M365 Connector) 1) Create an inbound connector that routes inbound mail to the inbound verifier host:2527. 2) Configure the connector to accept mail only from your provider IP ranges.

Client UX - Outlook add-in (optional) for badges. - Header-based verification works in security tooling without add-ins.

Reference: docs/EXCHANGE_AGENT_RUNBOOK.md

C) Postfix 1) Outbound: use relayhost or milter stub. 2) Inbound: use content_filter to inbound verifier. Reference: docs/GATEWAY_INTEGRATION.md

D) Hybrid (Split Domain) Route only a subset of domains / org units through the gateway for phased rollout.

E) API-Only Mode If you already have a gateway, call /v1/provenance/verify_headers directly.

Deployment Steps (Gateway Only)

Step 1: Start API

. .venv/bin/activate
PYTHONPATH=apps/api JWT_SECRET=dev-secret uvicorn server.app:app --host 0.0.0.0 --port 8125

Step 2: Outbound Relay

export API_TOKEN="$(JWT_SECRET=dev-secret python scripts/gen_token.py)"
export SMTP_HOST=smtp-relay.brevo.com
export SMTP_PORT=587
export SMTP_USER=your-user
export SMTP_PASS=your-pass
python poc/smtp_relay.py --listen-port 2525

Step 3: Inbound Verifier

export API_TOKEN="$(JWT_SECRET=dev-secret python scripts/gen_token.py)"
export INBOUND_SMTP_HOST=smtp-relay.brevo.com
export INBOUND_SMTP_PORT=587
export INBOUND_SMTP_USER=your-user
export INBOUND_SMTP_PASS=your-pass
python poc/smtp_inbound_daemon.py --listen-port 2527

Step 4: Point Mail Flow - Outbound: clients -> localhost:2525 - Inbound: provider -> localhost:2527

Email vs Certificate Provenance (Quick Comparison) See docs/EMAIL_VS_CERTIFICATE_COMPARISON.md.

M365 Quick Checklist - Outbound connector points to relay host:2525 - Inbound connector points to verifier host:2527 - TLS enabled between M365 and gateway (recommended) - Provider IP ranges whitelisted on inbound connector

M365 Admin Portal Steps (Screen-Style) Outbound Connector 1) Microsoft 365 Defender or Exchange Admin Center -> Mail Flow -> Connectors. 2) New connector: From "Microsoft 365" to "Partner organization". 3) Use "Only when I have a transport rule set up". 4) Smart host: gateway-relay.example.com:2525 5) Enable TLS and validate certificate (recommended).

Inbound Connector 1) Mail Flow -> Connectors -> New. 2) From "Partner organization" to "Microsoft 365". 3) Accept from these IP ranges (your SMTP provider). 4) Route mail through gateway-verifier.example.com:2527. 5) Require TLS where possible.

M365 Transport Rule Example Goal: Ensure outbound mail always routes through the gateway. 1) Mail Flow -> Rules -> New rule. 2) Apply this rule if: The sender is inside the organization. 3) Do the following: Redirect the message to gateway-relay@example.com (connector target). 4) Stop processing more rules.

M365 Pilot Rollout Plan 1) Week 1: Enable connector for a pilot domain or a test OU. 2) Week 2: Expand to 25% of outbound traffic. 3) Week 3: Expand to 50%. 4) Week 4: Expand to 100%, enable strict policy (allow_missing_provenance=false). 5) Ongoing: Monitor false positives, delivery delays, and audit logs.

Reliability & Hardening - Queues + retries are enabled by default. - Config knobs: - SMTP_MAX_ATTEMPTS - SMTP_RETRY_BACKOFF - SMTP_API_TIMEOUT - SMTP_INBOUND_QUEUE - SMTP_RELAY_QUEUE - IMAP watcher reliability: - IMAP_MAX_ATTEMPTS - IMAP_RETRY_BACKOFF - IMAP_API_TIMEOUT - IMAP_QUEUE_PATH

Policy Enforcement Configure sender domain policy in apps/api/server/config/policy.yaml:

required_sender_domains:
  - veriforensic.com
allow_missing_provenance: false
orgs:
  bank_org:
    required_sender_domains:
      - bank.com

Auditing & Retention - Enable: AUDIT_LOG_ENABLED=1 - Path: AUDIT_LOG_PATH=/var/log/nicrypt/audit.jsonl - Partition by org: AUDIT_LOG_PARTITION=1 - Export: make audit-export - Prune: make audit-prune

Key Management - Default: env variables ENC_PASSWORD/ENC_SALT - Keyring: USE_KEYRING=1 - File adapter: KEY_SOURCE=file + KEY_MATERIAL_PATH=/etc/nicrypt/key.json Reference: docs/KEY_MANAGEMENT.md

Rollout Plan (Recommended) 1) Pilot group (single domain or OU). 2) Observe verification rates and false negatives. 3) Gradually expand to 25%, 50%, 100%. 4) Enable strict policy (allow_missing_provenance=false).

Monitoring Checklist - Health endpoints respond 200. - Queue files are not growing unbounded. - Audit log size within retention policy. - Header stamps present on outbound mail. - Verified stamps on inbound mail.

Rollback - Bypass relay in mail flow. - Stop gateway daemons. - Disable strict policy.

Sizing Guidance (Rule of Thumb) - 1 gateway instance per 50k-100k emails/day - Scale horizontally by adding more relay/verifier instances - Keep API close to gateways for low latency

Client UX (Optional) - Gmail: poc/gmail-extension - Outlook: poc/outlook-addin - Header-based badges only (no client-side crypto)

Attachment Provenance (Documents) Sender side (institution) - Outbound gateway inspects attachments. - For each file, call /v1/provenance/embed_file and store ciphertext. - Stamp headers with attachment provenance (example below).

Recipient side - Client add-in reads headers and shows “Verified attachment” badge. - Optional “Verify attachment” button can call /v1/provenance/verify_headers or /v1/provenance/verify_file before opening.

Attachment header pattern (example) - X-Provenance-Attachment: filename=invoice.pdf; ciphertext=...; model=sshleifer/tiny-gpt2; bpt=4; ts=2026-02-16T10:00:00Z Endpoint - /v1/provenance/verify_attachment_headers accepts headers and returns per-attachment verification.

Troubleshooting - Missing provenance headers: check outbound relay flow. - Verified=false: check policy domain settings and keys. - Decrypt failures: verify ENC_PASSWORD/ENC_SALT. - High latency: scale gateways, increase timeouts. M365-specific - Connector test fails: confirm smart host DNS + port reachability. - TLS handshake errors: validate certificate chain and hostname match. - Inbound connector rejecting mail: verify provider IP allow-list. - Transport rule not firing: confirm rule scope and priority order. Common error codes - 421 4.7.0: Temporary TLS or routing issue (retry or check smart host). - 451 4.4.0: Transient failure to connect to gateway (check firewall). - 550 5.7.1: Policy rejection (connector or transport rule mismatch). - 535 5.7.3: Authentication failure to upstream relay (bad SMTP creds).
