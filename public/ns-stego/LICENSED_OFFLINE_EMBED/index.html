Licensed Offline Embed (Cyberpunk Mode)¶

This workflow is for “offline embedding, online verification” with vendor-controlled licensing:

  • The institution embeds provenance offline (no API calls) using the standalone SDK.
  • The embedded payload contains a vendor-signed license token (Ed25519 / JWKS-verifiable).
  • Anyone can verify the license token online (public key), and a verifier service can decrypt the ciphertext if it has the tenant’s Nicrypt keys.

It’s a practical control/compliance lever: - If the offline SDK is abused, the payload still carries a license identity (lic_id/jti), and you can revoke it.

Concepts¶

1) Vendor License Token (Ed25519)¶

The API can mint a license token: - POST /v1/licenses/issue (requires scope licenses:issue) - Anyone can verify the token signature: - POST /v1/licenses/verify (no auth) - GET /v1/.well-known/jwks.json (public keys)

2) Plaintext Layout (Before Nicrypt Encryption)¶

We encrypt a plaintext that looks like:

mh:<model_hash>|lic:<license_token>|<secret>
  • mh:<model_hash>| lets verifiers detect model/config mismatch (optional but recommended).
  • lic:<license_token>| provides vendor-controlled proof and revocation.
  • <secret> is the human meaningful claim you want to recover at verification time.

3) Feature Gates (Recommended)¶

License tokens can include a features object. The API can optionally enforce these:

  • Embed flows: require one of features.embed=true or features.offline_embed=true
  • Email signature issuance: require one of features.email_sign=true or features.signature_issue=true

Step-by-Step¶

A) Generate Vendor Keys (Ed25519)¶

openssl genpkey -algorithm Ed25519 -out vendor_ed25519_private.pem
openssl pkey -in vendor_ed25519_private.pem -pubout -out vendor_ed25519_public.pem

Run the API with:

export LICENSE_SIGNING_PRIVATE_KEY="$PWD/vendor_ed25519_private.pem"
export LICENSE_SIGNING_PUBLIC_KEY="$PWD/vendor_ed25519_public.pem"

B) Issue a License Token (Online, once per org / rotation period)¶

TOKEN="$(JWT_SECRET=dev-secret python scripts/gen_token.py)"

curl -sS -X POST http://127.0.0.1:8125/v1/licenses/issue \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"days_valid":30,"features":{"offline_embed":true}}'

Copy the token from the response.

B2) Refresh a License Token (Online, recommended)¶

For production, prefer short-lived tokens (e.g. 7–30 days) and refresh them on a schedule.

curl -sS -X POST http://127.0.0.1:8125/v1/licenses/refresh \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"token":"PASTE_OLD_TOKEN_HERE","days_valid":30}'

C) Embed Offline, Keep Ciphertext (Offline)¶

This produces: - ciphertext (store in headers / file metadata for online verification) - stego_text (innocent-looking cover text output, if you’re using LLM stego)

Key idea: capacity depends on payload size, so we do:

  1. Build + encrypt payload (includes license token)
  2. Estimate needed tokens
  3. Set max_new_tokens = needed + margin
  4. Recompute model hash with final max_new_tokens, re-encrypt, then embed
from nicrypt_stego.crypto import ficha
from nicrypt_stego.model_hash import compute_model_hash
from nicrypt_stego.bitcodec import estimated_tokens_for
from nicrypt_stego.provenance import ProvenanceWriter

LIC = "PASTE_LICENSE_TOKEN_HERE"
secret = "alice@example.com|2026-02-19|Licensed offline embed"
cover_prompt = "Subject: Test\n\nHello team,\nThis is a cover memo.\n"

cfg = dict(
    backend="mvp",
    model_name="sshleifer/tiny-gpt2",
    bits_per_token=3,
    device="cpu",
    top_k=64,
    redundancy=1,
    ecc_mode="repetition",
    ecc_symbols=16,
)

margin = 50

# Pass 1: encrypt with a provisional max_new_tokens (only to size ciphertext)
provisional_max = 300
mh1 = compute_model_hash(
    cfg["model_name"], cfg["backend"], cfg["bits_per_token"], provisional_max,
    cfg["device"], cfg["top_k"], cfg["redundancy"], cfg["ecc_mode"], cfg["ecc_symbols"],
)
pt1 = f"mh:{mh1}|lic:{LIC}|{secret}"
ct1 = ficha(pt1, "enc")
needed = estimated_tokens_for(
    ct1,
    bits_per_token=cfg["bits_per_token"],
    redundancy=cfg["redundancy"],
    ecc_mode=cfg["ecc_mode"],
    ecc_symbols=cfg["ecc_symbols"],
)
max_new_tokens = needed + margin

# Pass 2: recompute mh with the final max_new_tokens, then re-encrypt for correctness
mh2 = compute_model_hash(
    cfg["model_name"], cfg["backend"], cfg["bits_per_token"], max_new_tokens,
    cfg["device"], cfg["top_k"], cfg["redundancy"], cfg["ecc_mode"], cfg["ecc_symbols"],
)
plaintext = f"mh:{mh2}|lic:{LIC}|{secret}"
ciphertext = ficha(plaintext, "enc")

writer = ProvenanceWriter(max_new_tokens=max_new_tokens, **cfg)
stego_text = writer.embed_cipher(ciphertext, cover_prompt)

print("ciphertext:", ciphertext)
print("stego_preview:", stego_text[:120] + "...")

D) Verify Online (Ciphertext-Only)¶

Store the ciphertext in a durable channel (examples): - Email headers: X-Provenance-Ciphertext: <ciphertext> - PDF/DOCX metadata: X-Provenance-Ciphertext - Attachment header packing: X-Provenance-Attachment: filename=...; ciphertext=...; ...

Then online verification is one call:

curl -sS -X POST http://127.0.0.1:8125/v1/provenance/verify \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "ciphertext":"gAAAAA...",
    "model_name":"sshleifer/tiny-gpt2",
    "bits_per_token":4
  }'

If you set LICENSE_REQUIRED=1 on the API, verification will only succeed if: - the decrypted plaintext includes lic:<token>|..., and - that token is valid (signature, expiry), and - it is not revoked.

Revocation Storage Notes¶

Revocations are stored by jti. For PoC, JSON file storage is fine. For higher throughput deployments, switch to SQLite and enable a small cache:

export LICENSE_REVOCATIONS_BACKEND=sqlite
export LICENSE_REVOCATIONS_SQLITE_PATH=/var/lib/nicrypt/revocations.sqlite
export LICENSE_REVOCATIONS_CACHE_TTL_S=2.0

Practical Use Cases¶

  • Institution offline pipelines: stamp documents on-prem, verify via cloud service.
  • Edge signing: desktop apps / mail gateways embed without latency to a central API.
  • Compliance control: every provenance claim carries a vendor-issued license identity you can revoke.
