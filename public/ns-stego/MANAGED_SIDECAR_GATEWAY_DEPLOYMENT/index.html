Managed Sidecar Gateway Deployment (Customer-Hosted)¶

This is the “gateway as a service” operating model that matches what we tested locally, but deployed inside a customer environment (on‑prem or customer VPC). Nicrypt (or an integrator) can operate it, while the customer keeps data inside their perimeter.

What “Sidecar” Means Here¶

  • The customer hosts the gateway runtime (VM(s) or Kubernetes) in their environment.
  • The gateway relays mail only inside customer-controlled network paths.
  • The gateway forwards to the customer’s chosen upstream (M365, Gmail/Workspace, Brevo/SES, Postfix, etc.).

Components¶

  • Outbound relay (injector): accepts SMTP from the customer’s sending systems and injects attachment provenance headers.
  • Local port (default): 2525
  • Inbound stamper (verifier/stamper): receives the relayed message, stamps minimal UX (“ns-stego verified”) + machine markers for webmail verifiers, then forwards upstream.
  • Local port (default): 2527
  • API server (nicrypt-stego-api): keys, verification, signature issuance, policy, audit.
  • Local port (example): 8125

High-Level Flow¶

flowchart LR
  A[Customer apps / MTA] -->|SMTP| R[Outbound relay :2525]
  R -->|SMTP| S[Inbound stamper :2527]
  S -->|SMTP| U[Upstream provider\n(M365 / Workspace / Brevo / Postfix)]
  S -->|HTTP| API[nicrypt-stego-api :8125]
  R -->|HTTP (optional)| API

Notes: - The Gmail verifier extension can’t read message headers, so the inbound stamper must ensure the verification markers are present in the body in a Gmail-resilient way. - The API should be reachable from the gateway over the customer network (prefer private IPs).

Network & Ports¶

Minimum (pilot): - 2525/tcp inbound from customer send path → outbound relay - 2527/tcp inbound from outbound relay → inbound stamper (same host or internal network) - 8125/tcp inbound stamper → API (/v1/...)

Recommended: - Bind SMTP listeners to private interfaces only (no public exposure). - Allow-list sender IPs / subnets for 2525 and 2527.

Security Posture (Recommended Defaults)¶

SMTP hop security (pick one, strongest first): 1. mTLS between customer MTA and gateway, plus IP allow-lists 2. VPN / private peering + IP allow-lists 3. SMTP AUTH on the relay hop (least preferred in enterprise)

API security: - Use a least-privilege API token for the gateway. - Prefer file-based secrets (e.g., API_TOKEN_PATH, PROVENANCE_LICENSE_TOKEN_PATH) instead of environment literals. - Enable audit logging and forward logs to the customer SIEM if required.

Deployment Options¶

Option A: VM + systemd (Linux)¶

  • Deploy nicrypt-stego-api + gateway daemons on a hardened VM.
  • Install services via the repo’s systemd targets and set environment via /etc/... or systemd drop-ins.
  • Reference: docs/WINDOWS_SERVICE_RUNBOOK.md (concept), docs/GATEWAY_INTEGRATION.md (flow).

Option B: Kubernetes (customer VPC / on‑prem)¶

  • Run 3 Deployments:
  • API (nicrypt-stego-api)
  • relay (smtp_relay.py)
  • stamper (smtp_inbound_daemon.py)
  • Put SMTP behind an internal LoadBalancer / ClusterIP + an internal TCP ingress (depending on platform).
  • Use Kubernetes Secrets for API tokens and upstream SMTP credentials.

SMTP Provider Integration (Where You “Point Mail Flow”)¶

Common patterns: - M365: connectors/rules route outbound (and optionally inbound) through the sidecar gateway. - Reference: docs/EXCHANGE_AGENT_RUNBOOK.md, docs/EMAIL_GATEWAY_FLOW.md - Postfix: relayhost for outbound, content_filter for inbound stamping. - Reference: docs/GATEWAY_INTEGRATION.md - SMTP provider (Brevo/SES/Sendgrid): gateway forwards upstream using provider credentials.

Deliverability best practice: - Avoid having the gateway be the final public sender if it would break SPF/DKIM alignment. - Prefer forwarding to the customer’s official sending provider so DKIM/SPF remain consistent.

Operations Checklist¶

Before pilot: - Confirm SMTP forwarding works end-to-end (relay → stamper → upstream). - Confirm provenance verify works (Gmail + Thunderbird verifiers). - Confirm queue/retry behavior is acceptable (transient upstream failures). - Confirm no secrets are logged.

During production: - Monitor: - upstream SMTP auth failures - queue depth / retry counts - verification failures (policy: missing_provenance, license_missing, etc.) - Rotate: - API JWT secrets / signing keys per policy - SMTP creds (provider rotation) - Incident response: - export audit logs - snapshot gateway config and versions (git SHA / package build-info)

Smoke Test (Operator)¶

On the gateway host (or operator bastion):

make gateway-status

Then send a test message through the relay and verify it using: - Gmail extension (recipient experience) - Thunderbird add-on (admin/security experience)
