Certificate Provenance Sprint (Institutions)¶

Objective Enable institutions (universities, regulators, standards bureaus) to issue electronic certificates that recipients can verify as authentic and untampered.

Why it matters - Prevent forged qualification certificates and compliance letters. - Allow third‑party verification without contacting the issuer. - Preserve integrity even if the PDF is forwarded outside the original email.

Scope Two verification surfaces: 1) Email transport (headers + attachment provenance). 2) Document itself (embedded metadata / portal verification).

Deliverables 1) Issuance workflow (PDF) - [x] Script to embed provenance metadata into PDF/DOCX at issuance time (scripts/issue_certificate.py). - [x] Attach certificate ID + issuer ID + recipient ID + org ID + timestamp fields (embedded metadata). - [x] Record issuance manifest (JSONL) for audit (CERT_ISSUANCE_MANIFEST_PATH).

2) Email delivery flow - [x] Gateway stamps attachment provenance for certificate PDFs (reuse embedded metadata). - Set PROVENANCE_ATTACHMENT_MODE=metadata on poc/smtp_relay.py so X-Provenance-Attachment uses the attachment's embedded X-Provenance-Ciphertext (instead of generating a hash-only claim). - [ ] Optional NS-SIGNATURE line in email body (visible trust line). - [ ] Thunderbird/Gmail/Outlook verification surfaces show attachment status.

3) Standalone verification - [ ] CLI to verify a certificate PDF offline (no email). - [x] API endpoint to verify PDF/DOCX provenance (POST /v1/certificates/verify). - [x] CLI helper to call API verify (scripts/verify_certificate.py). - [ ] “Verify on portal” simple web flow (paste/upload).

4) Tamper detection - [x] Hash mismatch returns explicit status (tampered). - [x] Partial validation logic (valid issuer vs missing provenance vs tampered; reason surfaced in response).

5) Documentation - [ ] Issuer guide (what to embed, issuance steps). - [ ] Recipient guide (how to verify via email or file upload). - [ ] Threat model (forgery, re‑use, partial tamper).

Exit Criteria - At least one end‑to‑end demo: - Issue PDF -> send via gateway -> verify in mail client. - Verify the same PDF offline using CLI/API. - Docs published and linked from Docs Index.

Suggested APIs - POST /v1/certificates/issue (metadata + file -> provenance‑embedded file) - POST /v1/certificates/verify (file -> verified + issuer + cert_id)

Notes - This uses existing gateway attachment provenance + metadata embedding work. - Certificates should remain visually unchanged; provenance is stored in metadata.
