Institutional Rollout (One Pager)¶

This is a high-level rollout plan for deploying Nicrypt-Stego (ns-stego) across an institution for email anti-scam provenance and (optionally) document/certificate provenance.

Goal¶

Help staff and recipients answer, reliably: - “Did this email really come from the institution?” - “Was this attachment/certificate issued by the institution and not tampered with?”

What Gets Deployed¶

  • API server (nicrypt-stego-api): org keys, verification policy, license enforcement (optional), audit logging.
  • Email gateway (recommended):
  • Outbound relay: adds provenance headers (attachments/certificates).
  • Inbound stamper: adds minimal UX (“ns-stego verified”) and webmail-readable markers.
  • Verifiers (client UX):
  • Gmail extension (webmail).
  • Outlook add-in (M365).
  • Thunderbird add-on (strongest header visibility; ideal for security/admin users).

Trust Boundary (Decision Point)¶

Choose where secrets and enforcement live: - Hosted: Nicrypt runs the API, institution deploys verifiers/gateway config. - On‑prem: institution runs the API + gateway inside its network. - Hybrid: institution keeps keys/policy on‑prem; uses hosted services for scale where acceptable.

Best practice: keep keys + policy enforcement + license checks server-side.

Rollout Phases¶

  1. Pilot (1–2 weeks)
  2. Stand up the API in a test environment.
  3. Enable gateway flow for a single internal sending identity/domain.
  4. Roll out one verifier client (typically Gmail extension) to a small group.

  5. Define “Verified / Partial / Unverified” handling guidance for staff.

  6. Production Email (2–6 weeks)

  7. Gate outbound mail through relay; stamp inbound for webmail verification.
  8. Roll out verifiers org-wide (Gmail + M365/Outlook).
  9. Turn on audit logging + monitoring dashboards.

  10. Add incident playbooks (phishing response, escalation, forensic export).

  11. Attachments and Certificates (optional, 2–8 weeks)

  12. Stamp PDFs/certificates at issuance time (API “issue certificate” workflow).
  13. Enable attachment verification in verifiers/gateway.
  14. Establish recipient-facing verification instructions and support channels.

Operations Checklist (Ongoing)¶

  • Key management: rotation and secure storage.
  • Policy tuning: what to enforce vs warn; how to handle “partial”.
  • Revocations: revoke/expire licenses (if offline SDK is distributed).
  • Telemetry: audit logs, verification failures, upstream SMTP failures.
  • Documentation: keep a single “How to verify” guide for users.

Distribution Guidance (IP-Safe Defaults)¶

  • Freely distributable: verifiers (extensions/add-ons) + docs + typed client.
  • Controlled distribution: offline embedding SDK (license-gated, revocable).

Integrator / Partner Model (e.g., Tietoevry → Nordea)¶

Many institutions will deploy ns-stego through a systems integrator (SI) or managed service provider.

  • Institution (the issuer / trust anchor):
  • Owns the sending domain(s) and brand identity.
  • Controls org_id, allowed domains, verification policy, and cryptographic keys.
  • Should retain continuity if vendors/operators change (key and policy ownership).
  • Integrator (operator / implementer):
  • Implements and operates the API/gateway on behalf of the institution (hosted, on‑prem, or hybrid).
  • Integrates issuing/verification into the institution’s workflows (email gateway, certificate issuance, monitoring).
  • Operates under least-privilege service accounts and auditable access.

Best practice: keep issuer identity + keys + enforcement policy institution-controlled, while allowing integrators to run infrastructure and integrations.

Success Criteria¶

  • Users can verify institutional messages in the primary clients (Gmail + Outlook).
  • Attachments/certificates verify cleanly and detect tampering.
  • Audit trail supports compliance and incident response.
