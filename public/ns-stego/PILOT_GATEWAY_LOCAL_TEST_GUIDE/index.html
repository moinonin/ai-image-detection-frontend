Pilot: Local Gateway Test Guide (Customer Premises)¶

This guide is the step-by-step “runbook” for a pilot deployment on a customer machine/network where you want to validate the full email + attachment provenance loop:

  • SMTP relay (2525) injects provenance for attachments/certificates.
  • SMTP inbound stamper (2527) stamps minimal UX markers for verifiers (Gmail/Thunderbird).
  • ns-stego API (8125) provides verification and signature issuance.
  • Gmail extension / Thunderbird add-on verify what recipients see.

Assumptions: - You are running from the repo root: ns-stego/ - You have Python 3.11 and the project venv set up (.venv/) - You have working upstream SMTP credentials (Brevo/SES/M365 relay, etc.) - You can receive mail in Gmail and/or Thunderbird.

0) Environment Variables (What + Where)¶

Where to store env vars¶

  • Repo defaults: .env.example (placeholders only; treated as defaults)
  • Your real values: .env (overrides .env.example)

Do not put real secrets into .env.example.

Variables used by the gateway¶

API connectivity (used by both relay + inbound stamper): - API_BASE - Example: http://127.0.0.1:8125/v1 - What it does: points the gateway to the ns-stego API. - API_TOKEN (or API_TOKEN_PATH) - What it does: JWT used by the gateway to call API endpoints. - Recommended: use API_TOKEN_PATH to avoid fragile long env values.

Upstream SMTP (used by inbound stamper to forward to the real world): - INBOUND_SMTP_HOST / INBOUND_SMTP_PORT - INBOUND_SMTP_USER / INBOUND_SMTP_PASS - What it does: credentials to your upstream SMTP provider (Brevo, SES, etc.)

Relay -> Stamper hop (used by relay to forward locally): - SMTP_HOST / SMTP_PORT - Typical: SMTP_HOST=127.0.0.1, SMTP_PORT=2527

Provenance stamping: - STAMP_BODY (default 1) - If 1, inbound stamper adds visible “ns-stego verified” badge and machine markers. - PROVENANCE_ATTACHMENTS (default 1) - If 1, gateway emits attachment provenance markers for each attachment. - PROVENANCE_ATTACHMENT_MODE - Typical: metadata (best for certificate verification UX) - Other: hash (smaller marker; “tamper detect” only)

License enforcement (recommended for pilots that test licensing): - PROVENANCE_LICENSE_TOKEN_PATH - File containing a vendor license JWT. - Used when license enforcement is enabled on the API.

Minimal .env template (pilot)¶

Create/edit .env:

API_BASE=http://127.0.0.1:8125/v1

# Gateway calls to the API (prefer path form)
API_TOKEN_PATH=/tmp/api_token.jwt

# Relay forwards locally to inbound stamper
SMTP_HOST=127.0.0.1
SMTP_PORT=2527

# Inbound stamper forwards to upstream SMTP provider
INBOUND_SMTP_HOST=smtp-relay.brevo.com
INBOUND_SMTP_PORT=587
INBOUND_SMTP_USER=your-smtp-login
INBOUND_SMTP_PASS=your-smtp-key

# Stamping behavior
STAMP_BODY=1
PROVENANCE_ATTACHMENTS=1
PROVENANCE_ATTACHMENT_MODE=metadata

# License token (file)
PROVENANCE_LICENSE_TOKEN_PATH=/tmp/provenance_license.jwt

1) Ensure the API token has required scopes (or generate one)¶

The pilot typically needs a token that can: - verify provenance (provenance:verify) - verify attachment headers (provenance:verify) - issue compact signature tokens for Gmail marker strategy (signature:issue and/or signature:verify) - issue certificates (if you do step 6) (certificates:issue) - (optional) manage keys / licenses

Generate a dev token (local pilot)¶

If your API uses JWT_SECRET locally:

. .venv/bin/activate

export JWT_SECRET=dev-secret
python scripts/gen_token.py > /tmp/api_token.jwt

If you want to eyeball it:

head -c 32 /tmp/api_token.jwt && echo

Note: - In production, the institution will have their own signing secret / issuer and issuance process. For pilots, a dev token is acceptable.

2) Save API token into the token file¶

Recommended file (used by gateway installers and scripts): - /tmp/api_token.jwt

If you generated it in step 1, you’re already done.

3) Ensure you have a valid vendor license token (or issue one)¶

When the API is configured to require licenses for certain verification/issuance flows, you must provide a license token to the gateway (path recommended).

Save license token to file¶

Recommended file: - /tmp/provenance_license.jwt

Example:

printf '%s' "$LICENSE_TOKEN" > /tmp/provenance_license.jwt
chmod 600 /tmp/provenance_license.jwt

Issue a license token (API route)¶

If your API exposes a license issuance endpoint (admin-scoped), issue via curl:

API_BASE=http://127.0.0.1:8125/v1
API_TOKEN="$(cat /tmp/api_token.jwt)"

curl -sS -X POST "$API_BASE/licenses/issue" \\
  -H "Authorization: Bearer $API_TOKEN" \\
  -H "Content-Type: application/json" \\
  -d '{
    "org_id":"public",
    "lic_id":"lic_demo",
    "features":{"offline_embed":true,"signature_issue":true},
    "ttl_seconds":3600
  }' | tee /tmp/license_issue.json

Then extract and store the returned license_token:

python3 - <<'PY'
import json
data=json.load(open('/tmp/license_issue.json','r'))
print(data.get('license_token',''))
PY

Save it:

python3 - <<'PY'
import json, os
data=json.load(open('/tmp/license_issue.json','r'))
t=data.get('license_token','')
if not t:
  raise SystemExit('no license_token in response')
open('/tmp/provenance_license.jwt','w').write(t)
print('wrote /tmp/provenance_license.jwt')
PY
chmod 600 /tmp/provenance_license.jwt

4) Install and start the gateway services (relay + inbound)¶

This installs service definitions (launchd on macOS, systemd on Linux), enables them, and starts them.

macOS (launchd):

make install-services ENABLE_IMAP=0
make enable-services ENABLE_IMAP=0
make start-services ENABLE_IMAP=0

Linux (systemd):

make install-services ENABLE_IMAP=0
make enable-services ENABLE_IMAP=0
make start-services ENABLE_IMAP=0

Tip: - make restart-services ENABLE_IMAP=0 is the “do the right thing” idempotent target on macOS.

5) Confirm the gateway is healthy¶

Check listeners and health:

make gateway-status ENABLE_IMAP=0

Expected: - Port 2525 listening (relay) - Port 2527 listening (inbound stamper) - Inbound health endpoint returns JSON (may briefly “not ready” right after restart)

If emails aren’t sending: - Check inbound SMTP auth:

tail -n 200 /tmp/nicrypt-inbound.err
  • Confirm launchd/systemd is using real upstream creds:
UID=$(id -u)
launchctl print "gui/$UID/com.nicrypt.gateway.inbound" | grep -A6 INBOUND_SMTP_ 2>/dev/null || true

6) Stamp (issue) a certificate / PDF you will attach¶

This creates a stamped PDF that carries hidden provenance.

Example:

TOKEN="$(cat /tmp/api_token.jwt)"
LICENSE_TOKEN="$(cat /tmp/provenance_license.jwt)"

python scripts/issue_certificate.py \\
  --api-base http://127.0.0.1:8125/v1 \\
  --api-token "$TOKEN" \\
  --license-token "$LICENSE_TOKEN" \\
  --in docs/CoverLetterBinance.pdf \\
  --out /tmp/pilot_stamped.pdf \\
  --issuer-id "uni:example" \\
  --cert-id "cert:pilot-001" \\
  --recipient-id "person:alice" \\
  --secret "person:alice"

Sanity check verification (local API):

python scripts/verify_certificate.py \\
  --api-base http://127.0.0.1:8125/v1 \\
  --api-token "$TOKEN" \\
  --in /tmp/pilot_stamped.pdf

7) Activate verifiers (Gmail extension / Thunderbird add-on)¶

Gmail extension (Chrome)¶

  1. Install packaged artifact:
  2. dist/addons/gmail-extension.zip
  3. Chrome: chrome://extensions
  4. Enable “Developer mode”
  5. “Load unpacked”:
  6. unzip gmail-extension.zip to a folder
  7. select that folder (contains manifest.json)
  8. Open extension Options and set:
  9. Base URL: http://127.0.0.1:8125/v1 (pilot/local)
  10. Token: leave blank for public verify, or paste your JWT if your verify requires it

Thunderbird add-on¶

  1. Install:
  2. dist/addons/thunderbird-addon.xpi
  3. Thunderbird → Add-ons and Themes → gear icon → “Install Add-on From File…”
  4. Set in add-on settings:
  5. API Base: http://127.0.0.1:8125/v1
  6. API Token: $(cat /tmp/api_token.jwt) (Thunderbird can read headers; token often used in pilots)

8) Send an email with the stamped attachment and verify it¶

Send through the relay so the gateway can inject/stamp:

python3 scripts/send_signed_attachment.py \\
  --mail-to your.recipient@example.com \\
  --attach /tmp/pilot_stamped.pdf \\
  --qa-id "pilot-$(date +%Y%m%d-%H%M%S)" \\
  --save-eml /tmp/nicrypt-last.eml \\
  --api-token "$(cat /tmp/api_token.jwt)" \\
  --license-token-path /tmp/provenance_license.jwt

Local verify of the generated .eml (before it hits the outside world):

python scripts/verify_email.py /tmp/nicrypt-last.eml \\
  --api-base http://127.0.0.1:8125/v1 \\
  --api-token "$(cat /tmp/api_token.jwt)" \\
  --verdict

Then verify in the recipient client: - Gmail: open the email → click “Verify provenance” → expect “Verified sender” + attachments verified. - Thunderbird: open the email → click “Verify provenance” → expect sender + attachment verification.

Troubleshooting (Fast)¶

Gateway sends but upstream rejects (SMTP 535 auth): - Verify INBOUND_SMTP_USER/INBOUND_SMTP_PASS in .env - Restart services: make restart-services ENABLE_IMAP=0

Gmail says “No provenance markers”: - Ensure STAMP_BODY=1 - Ensure inbound stamper is in the path (relay → inbound → upstream) - Ensure your message body includes the minimal marker badge (ns-stego verified)

Attachment shows unverified: - Ensure PROVENANCE_ATTACHMENTS=1 - Ensure PROVENANCE_ATTACHMENT_MODE=metadata for certificate-style flows - Confirm license token is valid/not expired (if required)
