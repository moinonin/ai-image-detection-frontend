Email Provenance: Verified Sender for Anti‑Scam Email¶

Purpose Provide cryptographic proof that an email was authored by a legitimate organization, enabling recipients and mail systems to detect impersonation and phishing.

Related - Certificate issuance and verification: docs/CERTIFICATE_PROVENANCE_SPRINT.md

Email vs Certificate Provenance (Quick Comparison) See docs/EMAIL_VS_CERTIFICATE_COMPARISON.md.

Goals - Stop sender impersonation even when SPF/DKIM/DMARC pass or are bypassed. - Verify the content itself, not just the sending domain. - Make verification visible to users via a simple trust indicator. - Support on‑prem deployments for regulated institutions.

Non‑Goals - Replace SPF/DKIM/DMARC. This complements them. - Guarantee safety of all links or attachments. - Prevent all social engineering. It verifies origin only.

High‑Level Flow

Outbound (Sender Organization) 1. Compose email content. 2. Generate provenance payload (org, timestamp, campaign, signer id). 3. Encrypt payload with Nicrypt (institution‑managed keys). 4. Embed ciphertext into the email body using steganography. 5. Send email normally.

Inbound (Recipient) 1. Mail gateway or client extracts ciphertext from body. 2. Decrypts using the institution’s public verification path (or shared key). 3. Verifies model hash and key id. 4. Shows Verified/Unverified status in the UI.

Architecture Options

  1. Mail Gateway Integration (Recommended)
  2. Outbound: inject provenance in the final hop before SMTP.
  3. Inbound: verify for internal recipients and annotate headers.
  4. Pros: centralized, scalable, no client plugins required.

  5. Cons: requires gateway integration and routing changes.

  6. Client Plugin (Outlook / Gmail)

  7. Outbound: plugin embeds on send.
  8. Inbound: plugin verifies and renders badge.
  9. Pros: no gateway changes, faster pilot.

  10. Cons: per‑user installation and updates.

  11. Application‑Level Integration

  12. For custom CRM or internal portals that send email.
  13. Embed and verify within the app’s email pipeline.

Verification UX - Verified: “Verified Sender” badge with org name and timestamp. - Unverified: “Sender not verified” warning with a short explanation. - Tampered: “Content altered” warning if extraction fails or mismatches.

Provenance Payload Format (Example) org=AcmeBank|dept=Consumer|timestamp=2026-02-15T10:32Z|campaign=FraudAlert|key_id=key_9f4d2

Security Model - Keys remain inside the institution’s boundary. - Only authorized systems can encrypt (embed). - Verification can be performed by recipients or gateways using allowed keys. - Model hash ties the message to the configured embedding model for consistency.

Threats Addressed - Domain spoofing and look‑alike domains. - Compromised forwarding chains. - Content forgery and copy‑paste attacks.

Threats Not Fully Addressed - A compromised sender system (attacker can embed valid provenance). - Social engineering that uses genuine verified messages. - Malicious links or attachments (requires separate scanning).

Operational Considerations - Key rotation: rotate keys on a schedule and maintain a grace window for verification. - Model locking: fix model hash for long‑term verification. - Policy: define which communications must be verified (e.g., finance, HR, compliance). - Logs: record verification outcomes for audit and incident response.

Integration Steps

Phase 1: Pilot - Pick one high‑risk communication stream (bank alerts or HR memos). - Deploy embedding at send time only. - Measure verification success and false negatives.

Phase 2: Verification UI - Add badge to internal mail client or gateway‑injected header. - Add warnings for unverified messages.

Phase 3: Institution‑wide - Extend to all official communications. - Enforce verified status for trusted channels.

API Usage (Minimal)

Embed (Outbound) POST /v1/provenance/embed Body: { "secret": "org=AcmeBank|dept=Consumer|timestamp=2026-02-15T10:32Z|campaign=FraudAlert", "cover_prompt": "Subject: Policy Update...", "backend": "mvp", "bits_per_token": 3, "max_new_tokens": 700 }

Verify (Inbound) POST /v1/provenance/verify Body: { "ciphertext": "gAAAAABl...5g", "model_name": "sshleifer/tiny-gpt2", "bits_per_token": 4 }

Stego Quality Examples (Embed Cipher)

These examples use POST /v1/provenance/embed_cipher so you can demonstrate "innocent" cover text while embedding an existing ciphertext.

Config notes: - Demo model: sshleifer/tiny-gpt2 (local + lightweight). - ECC: ecc_mode="reed-solomon" with ecc_symbols=16 for robustness. - stego_text below is representative output style (your exact text will vary).

Visible Signature Tokens (email-friendly) - Use /v1/signature/token to generate a short token. - Embed the token in a human-visible signature block:

Example: Best regards, Nordea Bank Oy NS-SIGNATURE: v1.abcd.efgh

Verification - Use /v1/signature/verify to validate the token and retrieve the signed payload. - Gmail/Outlook helpers can parse NS-SIGNATURE: and verify automatically.

Scripted issuance (CLI)

TOKEN="..." SENDER="Nordea Bank Oy" NOTE="Best regards" scripts/signature_token.sh

PowerShell

$env:TOKEN="..."
$env:SENDER="Nordea Bank Oy"
$env:NOTE="Best regards"
.\scripts\signature_token.ps1

Gateway automation (no user action) - Set SIGNATURE_MODE=visible in the SMTP relay. - The relay appends NS-SIGNATURE: ... to outgoing emails automatically. - Optional: set PROVENANCE_SENDER and PROVENANCE_SIGNATURE_NOTE for consistent branding.

Diagram (Outlook → Relay → Internet)

flowchart LR
  A["Outlook Client"] --> B["SMTP Relay (Nicrypt Gateway)"]
  B --> C["Internet / Recipient MX"]
  B --> D["Signature Token API"]
  D --> B
  B --> E["Adds NS-SIGNATURE to Body + Headers"]

Practical use cases - Customer service and banking alerts: append a verifiable signature line. - HR and compliance emails: prove the sender without altering the body. - Press releases and public announcements: readers can verify authenticity. - Support tickets and incident responses: add a tamper-evident signature line.

Rollout Checklist - Select model and lock hash. - Configure keys and rotation policy. - Integrate outbound embed at send time. - Integrate inbound verify at receive time. - Define UI badge and warning copy. - Add monitoring and audit logs.

Success Metrics - Verified percentage on outbound streams. - False negative verification rate. - Reduction in phishing incidents. - Compliance audit readiness.

Gmail and Outlook Implementation Notes

Gmail (Google Workspace) - Outbound: use a Gmail add‑on or Apps Script that calls the embed API before send. - Inbound: add a Gmail add‑on that extracts from the message body and calls verify. - UI: show a Verified badge near the sender name and a warning if unverified. - Admin: restrict add‑on installation to approved domains and users.

Outlook (Microsoft 365) - Outbound: use an Outlook add‑in (Office.js) to embed before send. - Inbound: use an Outlook add‑in or Exchange transport rule with a verification service. - UI: add a ribbon indicator or message header banner for verified senders. - Admin: deploy add‑ins centrally via Microsoft 365 admin center.

Extension Monetization and Distribution (Recommended Path)

Goal Monetize via an enterprise license while keeping the extension free to install.

Approach - Ship the extension at no cost in the store or via managed deployment. - Access requires API tokens tied to an institutional license. - Tokens are issued and rotated by the institution’s admin.

Benefits - Fits institutional procurement (annual license + support). - Avoids consumer payment friction and store policies. - Allows centralized revocation and auditability.

Distribution Options - Managed deployment via Google Workspace Admin or Microsoft 365 Admin. - Private distribution for regulated environments. - Public store listing for easier discovery and trials.

Phishing Simulator Test Plan

Goal Validate that verified messages pass and impersonation attempts are flagged.

Setup - Create a “legitimate” sender workflow that embeds provenance. - Create a “fraudulent” workflow that does not embed or uses wrong keys.

Test Cases 1) Verified message, correct key Expected: Verified badge, extracted payload matches sender metadata.

2) Verified message, altered content Expected: Verification fails or tampered warning.

3) Unverified message, spoofed display name Expected: Unverified warning shown.

4) Forwarded verified message Expected: Still verifies if content intact.

5) Forwarded and edited message Expected: Verification fails or tampered warning.

6) Mixed HTML/plain text Expected: Extractor handles plaintext fallback or warns if content lost.

Measurements - Verification success rate by client (web, mobile, desktop). - Time to verify (client latency). - False positives and false negatives.
